# T1003.001 - LSASS Credential Dumping (ProcDump)

**Host:** DESKTOP-18T77L4
**Technique:** T1003.001 - OS Credential Dumping: LSASS Memory
**Tool:** `C:\Tools\Procdump\procdump64.exe -accepteula -ma lsass.exe`

## Summary

ProcDump was used to dump the LSASS process on the target host, a technique commonly used to harvest cached credential material for offline cracking or pass-the-hash attacks. Wazuh's built-in detection for this technique (rule 92900) never fired, due to a stale access-mask allowlist that predates how modern Windows processes actually request access to LSASS. Two custom rules were written to close the gap, and both are validated against live attack traffic in this write-up. The custom-rule work also surfaced a second, independent finding about detection design: a precise rule and a broad rule catch different things, and both are worth keeping.

## Detection Gap: Built-in Rule 92900

Rule 92900 is Wazuh's built-in detection for credential access via Sysmon Event 10 (ProcessAccess), but it only matches `GrantedAccess` values of `0x1010` or `0x40` - an allowlist that predates current Windows/Sysmon access-mask conventions. A `rule.id:92900` search in Discover returns no results across the full test session, despite ProcDump successfully dumping LSASS multiple times.

The actual Sysmon Event 10 record for the ProcDump-to-LSASS access, captured directly in Wazuh Discover, confirms the cause:

```
sourceImage:       C:\Tools\Procdump\procdump64.exe
sourceUser:        DESKTOP-18T77L4\paritvr
targetImage:       C:\Windows\system32\lsass.exe
targetUser:        NT AUTHORITY\SYSTEM
grantedAccess:     0x1fffff
utcTime:           2026-09-20 03:56:15.743
sourceProcessGUID: {7ca8ebe5-595f-6aaf-4909-000000000e00}
targetProcessGUID: {7ca8ebe5-039a-6aae-0c00-000000000e00}
```

`procdump64.exe -ma` requests `0x1FFFFF` (`PROCESS_ALL_ACCESS`) - a value well outside rule 92900's allowlist, which is why it never fired.

## Evidence

- **ProcDump execution and dump file** - `procdump64.exe -accepteula -ma lsass.exe` completed successfully across multiple attempts, writing 54–72 MB dump files to `C:\Tools\lsass_dump.dmp` / `lsass_dump-1.dmp`, confirmed via terminal output.
- **Independent corroboration** - Windows Defender's behavioral engine flagged the same activity as `Behavior:Win32/DumpLsass.A!attk`, confirming the dump independent of Wazuh.
- **Rule 92900's allowlist** - the rule's own definition (`/var/ossec/ruleset/rules/0945-sysmon_id_10.xml`) matches only `GrantedAccess` values `0x1010` or `0x40`.
- **Custom rule 100004 fired on the confirmed event** - `rule.id: 100004`, `level: 14`, `firedtimes: 2`, `mitre.id: T1003.001`, description "Possible credential dumping: process access to LSASS via ProcDump" - a precise match tied directly to the record above.
- **Custom rule 100010 also fired in the same test window** - `rule.id: 100010`, `level: 12`, `groups: local, sysmon, attack`, description "Possible LSASS memory access - credential dumping attempt," recorded roughly a second apart from the 100004 event, consistent with ProcDump generating more than one ProcessAccess log entry per run.

## Detection Engineering: Custom Rules 100004 and 100010

Two custom rules cover this technique:

| Rule | Level | Scope | Purpose |
|---|---|---|---|
| **100004** | 14 | `sourceImage=procdump` + `targetImage=lsass.exe` | High-confidence, page-worthy alert |
| **100010** | 12 | Any Event 10 access to `lsass.exe` | Broad safety net |

**Initial rule dependency issues.** Both rules failed to fire on the first test pass, for reasons unrelated to access masks:

- Rule 100004 referenced `<if_group>sysmon_event10</if_group>` (no underscore). Wazuh's built-in Event 10 rule (92900) actually depends on the group `sysmon_event_10` (with an underscore), so rule 100004's parent condition never resolved.
- Rule 100010 referenced `<if_sid>61603</if_sid>`. Rule 61603 is the base classification rule for Sysmon **Event ID 1** (process creation), not Event ID 10:
  ```xml
  <rule id="61603" level="0">
    <if_sid>61600</if_sid>
    <field name="win.system.eventID">^1$</field>
    <description>Sysmon - Event 1: Process creation $(win.eventdata.description)</description>
    <group>sysmon_event1,</group>
  </rule>
  ```
  Rule 100010 was checking for a parent that can only ever match process-creation events, so it could never trigger on a process-access record.

Both dependency conditions were corrected - 100004's group name to `sysmon_event_10`, 100010's condition switched to `if_group: sysmon_event_10` - and the manager was restarted to reload the ruleset.

**Validation.** After the fix, rule 100010's first fires were on `VBoxService.exe` (the VirtualBox Guest Additions service, running as `NT AUTHORITY\SYSTEM`) querying `lsass.exe` with `GrantedAccess: 0x1400`, already at 999 fires within the test window from that single source - routine VM housekeeping, not an attack. Rule 100004 correctly stayed silent on this event. On a subsequent ProcDump run, both rules fired correctly on the real attack traffic (see Evidence, above), confirming they detect the intended technique in addition to rule 100010's known noise on unrelated system activity.

**Why keep both rules.** Rule 100004 is narrow by design - it only matches when `sourceImage` contains "procdump" *and* `targetImage` is `lsass.exe`. That precision is why it stayed silent on the `VBoxService.exe` traffic, but it is also a blind spot: any credential-dumping technique that doesn't route through a binary named "procdump" (Mimikatz, the `comsvcs.dll` MiniDump technique, Task Manager's built-in dump option, or ProcDump simply renamed) would never trigger it. Rule 100010 is the safety net for that blind spot - it fires on any Event 10 access to `lsass.exe`, regardless of tool - but the same lack of scoping that gives it broad coverage makes it noisy. In practice, rule 100004 is the rule to alert on directly; rule 100010 is better routed to a lower-priority feed, or tuned further with an access-mask filter or an allowlist for known-benign source images, before treating its fires as actionable on their own.

## MITRE ATT&CK Mapping

- **Tactic:** Credential Access
- **Technique:** T1003 (OS Credential Dumping) - sub-technique T1003.001 (LSASS Memory)

## Impact

A successful LSASS dump exposes cached credential material - password hashes and, depending on configuration, plaintext credentials or Kerberos tickets - for every account that has logged into the host. This enables offline password cracking or pass-the-hash attacks against other systems, escalating a single-host compromise into broader credential theft across an environment.

## Response

- **Detect:** extend rule 92900 (or write a replacement) to match `0x1FFFFF` and other modern access masks used by common dumping techniques (Mimikatz, `comsvcs.dll` MiniDump, Task Manager dump, ProcDump), rather than relying on a small set of hardcoded legacy values. In the meantime, run rule 100004 as the primary alert and route rule 100010 to a lower-priority feed or add an access-mask/allowlist filter before treating its fires as actionable on their own.
- **Contain:** isolate the host immediately and treat every credential that had an active session on it as compromised - force a reset for all of them.
- **Harden:** enable Credential Guard / LSA Protection (RunAsPPL), which blocks unsigned processes from opening a handle to LSASS at all. This would have stopped ProcDump outright, independent of any log-based detection.
